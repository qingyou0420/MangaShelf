# MangaShelf 迭代方案（个人自用版）

> 写作日期：2026-08-23，基于 `main` 分支 v2.5.0 的实际代码通读。
> 定位不变：**一个人、一台 Windows 电脑、本地文件夹里的漫画**。所有建议都围绕"读得舒服、跑得稳、改得动"三件事，不做任何产品化 / 商业化的事情。

---

## 一、现状概要

### 1.1 技术栈与架构

| 层 | 技术 | 位置 |
|---|---|---|
| 桌面壳 | Tauri 2（NSIS 安装包，仅 Windows） | `src-tauri/tauri.conf.json` |
| 后端 | Rust（rusqlite / zip / image / ureq） | `src-tauri/src/`（约 4900 行） |
| 前端 | React 19 + TypeScript + Vite 7 | `src/`（约 6000 行，含测试） |
| 数据 | 单个 SQLite 索引库（WAL 模式），默认 `E:\书架\manga-library.sqlite` | `src-tauri/src/db.rs`、`config.rs` |
| 测试 | vitest（前端各视图都有测试）+ cargo test（后端逻辑测试很全） | `*.test.tsx`、各 `.rs` 文件内 `mod tests` |
| 发版 | 推 `v*` 标签触发 GitHub Actions 打包上传 Release | `.github/workflows/release.yml` |

数据流很简单清晰：前端 `invoke` 调 Rust 命令（`src-tauri/src/lib.rs` 里注册了 23 个命令），Rust 扫文件夹 / 解压 / 读写 SQLite，图片通过 Tauri asset 协议直接喂给 webview。没有服务器、没有账号、没有遥测——这个底子非常适合自用，应当保持。

### 1.2 已经做得不错的部分

- **扫描是增量且幂等的**：`library.rs` 先用"廉价签名"（一二级目录的文件名 + 大小 + 修改时间，`bookshelf.rs::cheap_signature`）快速跳过没变的漫画，变了才算完整指纹（`v2:` FNV 摘要）并重扫章节；文件夹消失只标"未匹配"，绝不删用户文件。这套设计有完整测试覆盖。
- **阅读器功能齐**：翻页 / 滚动 / 双页三种模式、左开右开、四种适配、跨话翻页、进度按话记忆、章节侧栏、全屏、鼠标滚轮和键盘快捷键、工具栏自动隐藏（`ReaderView.tsx`）。
- **压缩包体验完整**：zip/cbz 解压到 `.manga-library/extract` 缓存并有 2GB LRU 自动清理；rar/cbr 自动找 7-Zip / WinRAR 命令行，找不到时给出人话错误提示（`bookshelf.rs`）。
- **进度和元数据不怕重扫**：改名、加标签、收藏、阅读进度在重扫时都会保留（`library.rs` 的 `merge_chapter_progress` + 测试 `scan_preserves_progress_and_custom_metadata`）。
- **更新通道够用**：启动查一次 GitHub Release，侧栏出现"更新 vX.Y.Z"按钮，一键下载并拉起安装器（`update.rs`、`useAppUpdate.ts`）。
- **本地有统一验证入口**：`npm run verify` 一条命令跑前端测试、构建、cargo test、clippy（`package.json`）。

### 1.3 现存痛点（都在真实代码里，标注了出处）

**A. 可靠性 / 数据安全**

1. **索引库没有任何备份**。阅读进度、收藏、手工元数据全在一个 sqlite 文件里，且默认放在书架目录（`E:\书架\manga-library.sqlite`）。误删书架文件夹、磁盘出坏道，几年的阅读记录一次归零。目前没有任何自动备份逻辑（全仓库搜不到 backup 相关代码，旧的备份设计只存在于 `docs/superpowers/` 的历史文档里，针对的是已经移除的 MangaCon 数据库）。
2. **rar 页数可能是假的**：`bookshelf.rs::count_images_in_archive` 里 rar 列举失败时 `unwrap_or(1)`，即"没装 7-Zip 时这话显示 1 页"。不算大问题，但界面会骗人。

**B. 性能（大书架场景）**

3. **每打开一个压缩包章节，就把整个解压缓存目录递归算一遍大小**：`bookshelf.rs::list_archive_pages` 每次调用 `prune_extract_cache`，后者对缓存下每个目录跑 `dir_size` 递归遍历。缓存接近 2GB、目录多时，每次开话都白付一次全缓存遍历的代价。（假设：机械硬盘上会更明显；未在真实机器实测，需验证。）
4. **压缩包必须整包解压完才能开始看**：`list_chapter_pages` 要等所有图片解压完才返回页列表。大体积单话 zip 意味着"正在解压…"要等完。有进度提示，但没有"解压到第一页就先看"的路径。
5. **自动扫描无开关**：启动后台扫一次 + 窗口每次重新可见且距上次超过 2 分钟就再扫（`useLibrarySession.ts` 的 `onVisibility`）。书架大、盘慢时切窗口回来可能感到卡或硬盘响。（假设：SSD 上无感，HDD 上可感，需按实际机器验证。）

**C. 正确性边角**

6. **半话排序不对**：`bookshelf.rs::chapter_ordinal` 只取第一段连续数字，`第10.5话` 的序号是 10，之后靠字符串比较，`.` 排在 `话` 前面，结果 **第10.5话 排在 第10话 前面**。有 x.5 话的漫画目录会串顺序。
7. **章节类型判断很粗**：`classify_chapter_kind` 靠 `contains("卷")`、`starts_with('第')` 等关键字，像"单行本卷末附录"会被当成"卷"。自用可容忍，但可以做个手动改类型的兜底。
8. **更新请求的 User-Agent 写死了版本号**：`update.rs` 第 16 行 `const USER_AGENT: &str = "MangaShelf/2.5.0";`，以后升版本这里不会跟着变（应改用 `env!("CARGO_PKG_VERSION")` 拼接）。

**D. 代码可维护性（一个人以后还改得动）**

9. **`useLibrarySession.ts`（577 行）是个"什么都管"的大 Hook**：路径、扫描、系列页、阅读器服务、增删改查全在里面。`ReaderView.tsx`（842 行）里有十几个 `useRef` 镜像 state，改翻页逻辑时容易漏同步。`App.css` 单文件 1448 行。都能跑、有测试兜底，但每次改动的心智负担在涨。
10. **前后端各写了一份路径逻辑**：默认书架 `E:\书架` 与 db 文件名在 Rust（`config.rs`）和 TS（`lib/defaults.ts`）里各有一份；`cacheRootForPath`（TS）和 `cache_root_for`（Rust）逻辑重复，且 TS 版手写反斜杠处理。两边改一漏一就出 bug。
11. **残留的死代码 / 历史包袱**：
    - `update.rs` 里整套"扫本地目录找安装包"的逻辑（`check_local_installer_updates`、`default_search_dirs` 及其中写死的 `D:\Grisia Studio\...` 机器路径）——前端实际只调 GitHub 检查，这套只有测试在用；
    - `library.rs` 里 `save_read_progress` / `set_comic_favorite` 等一组包装函数，正式命令走的是 `lib.rs` 的 `LibraryDbState` 缓存连接，这组函数只剩测试在调；
    - `docs/superpowers/` 四份计划 + 一份设计全是 MangaCon Companion 时代的文档，描述的截图 / 鼠标自动化 / 任务队列功能已不存在于代码中，会误导以后翻文档的自己。

**E. 体验小噪点**

12. 书库网格键盘导航是一维的：`LibraryView.tsx` 里 `ArrowDown` 和 `ArrowRight` 都是"下一个"，在网格里按"下"不会跳到下一行同列。
13. 阅读器没有"跳到第 N 页"的输入（有拖动条）、没有临时放大查看细节（Ctrl+滚轮 / 双击放大）。
14. 滚动模式的占位高度默认猜 900px（`ReaderView.tsx::spacerPx`），长条漫画未加载部分的滚动条会跳。
15. 删除书目只删数据库行（`db.rs::delete_comic`），`.manga-library/covers` 里对应的封面缩略图会永久残留；「查看缓存」也只统计 extract 目录，不含 covers / cover-preview。

## 二、迭代原则

给自己定的规矩，后面每一项建议都遵守：

1. **数据第一**：阅读进度和手工元数据是唯一不可再生的东西，任何改动前先把"索引库备份"做掉。漫画文件永远只读。
2. **保持现有技术栈**：Tauri + React + SQLite 不动。不引服务器、不引 ORM、不引大型状态库、不做多平台。
3. **低仪式感**：不搞分支规范、不搞发版流程文档、不搞 issue 模板。改一件事 → `npm run verify` 过 → 提交。现有的"每个行为都有测试"的习惯是最值钱的仪式，保留它。
4. **先修会咬人的，再做锦上添花**：可靠性 > 正确性 > 每天摸得到的体验 > 视觉 > 代码洁癖。
5. **删除也是迭代**：一个人维护的项目，死代码就是负资产，该删删。
6. **每一批改动可独立回退**：不把重构和功能混在一个提交里（这条在旧设计文档里就有，实践得也不错，继续保持）。

## 三、综合方案

优先级说明：**P0 = 尽快做（防丢数据/明显 bug）**，P1 = 值得做（日常舒适度），P2 = 有空再做。
工作量：小 = 一两次专注改动；中 = 需要动多个文件、补几个测试；大 = 涉及结构调整、要分步走。

### 3.1 代码 / 架构

#### ① 索引库自动备份 —— P0 · 小

- **为什么**：见痛点 1，这是全项目唯一"坏了哭都没用"的点。
- **方向**：启动或每次扫描完成后，把 sqlite 复制一份到 `%LOCALAPPDATA%\MangaShelf\backups\`（和书架不同盘的目录），文件名带日期，保留最近 7~10 份自动轮换。SQLite 在 WAL 下直接复制文件有微小风险，稳妥做法是用 rusqlite 自带的 Online Backup API（`rusqlite::backup`），几十行代码。设置页加一行"备份目录 + 打开文件夹"即可，不需要恢复 UI（真出事了手动把文件拷回去就行）。

#### ② 修 `chapter_ordinal` 半话排序 —— P0 · 小

- **为什么**：见痛点 6，直接影响目录顺序这种"每天看得到"的正确性。
- **方向**：`bookshelf.rs::chapter_ordinal` 解析数字时允许一段小数（`10.5`），补一个 `第10话 / 第10.5话 / 第11话` 顺序的测试。函数本来就返回 `Option<f32>`，改动面很小。

#### ③ 清理死代码与历史文档 —— P1 · 小

- **为什么**：见痛点 11。一个人维护，翻到一段"不知道还有没有用"的代码，成本比删掉再找回来高得多。
- **方向**：
  - 删 `update.rs` 的本地安装包扫描（`check_local_installer_updates`、`default_search_dirs`、`push_release_ancestors` 及机器路径）和对应测试，只留 GitHub 通道；顺手修痛点 8 的 User-Agent。
  - 删 `library.rs` 里只有测试在用的包装函数，测试直接建 `LibraryDatabase` 调用。
  - `docs/superpowers/` 整个移到 `docs/archive/`（或直接删，git 历史里有），避免误导。

#### ④ 收敛前后端重复的路径逻辑 —— P1 · 中

- **为什么**：见痛点 10，这是最容易"改一边忘另一边"的隐性 bug 源。
- **方向**：让 Rust 当唯一权威。`load_library` 已经会把解析后的 `databasePath`/`bookshelfRoot` 返回给前端，可以再补一个小命令（如 `resolve_paths`）让前端的 `databasePathFor`、`cacheRootForPath` 改为调后端，TS 里删掉手写的反斜杠拼接。localStorage 里只存"用户选了什么"，不存推导结果。

#### ⑤ 拆分 `useLibrarySession` 与 `ReaderView` —— P2 · 中

- **为什么**：见痛点 9。不是现在的 bug，而是"半年后还想改得动"的投资。
- **方向**：不引状态库，只按职责拆：`useLibrarySession` 拆出 `useScan`（扫描 + 进度 + 取消）、`usePaths`（路径与持久化）两个子 Hook；`ReaderView` 把纯函数（`nextSpreadIndex`、`lastSpreadStart`、`alignSpreadIndex` 等翻页数学）挪到独立文件并直接对它们写单测。每次只拆一块，拆完 `verify` 必须全绿。**建议只在"确实要改那块逻辑"时顺手拆，不为拆而拆。**

#### ⑥ 降低缓存清理的频率 —— P1 · 小

- **为什么**：见痛点 3，每开一话付一次全缓存遍历。
- **方向**：`list_archive_pages` 里不要每次都 `prune_extract_cache`，改成进程内记一个"上次清理时间"，比如 10 分钟内不重复清；或只在缓存新增内容后清。几行改动。

### 3.2 功能

#### ⑦ 压缩包"边解压边看" —— P1 · 中

- **为什么**：见痛点 4，大 zip 的等待是目前阅读链路里最长的一次硬等。
- **方向**：最省事的版本：解压时按自然序先解前几张，`list_chapter_pages` 提前返回已就绪页 + 后台继续解压 + 用现有 `library-extract-progress` 事件通知前端追加页数。不需要改成按页随机解压那种复杂方案。先做 zip/cbz；rar 走外部命令行，保持整包解压不动。

#### ⑧ 「标记已读 / 未读」 —— P1 · 小

- **为什么**：现在唯一的进度入口是"真的翻到那一页"。补档旧漫画、跳过不想看的话时，没法直接把某话或整本标成已读；清除进度倒是有（`clear_read_progress`）。
- **方向**：章节右键或长按菜单加"标为已读 /未读"（把 `read_progress_page` 置为 `page_count - 1` 或 0）；系列页加"全部标为已读"。数据结构完全不用动。

#### ⑨ 自动扫描开关与手感 —— P1 · 小

- **为什么**：见痛点 5。自动扫描本身是好功能（书架加了新话回来就能看到"最近更新"），但应该由用户决定。
- **方向**：设置页加一个开关"切回窗口时自动检查书架更新"（默认开，状态存 localStorage），`onVisibility` 里尊重它。顺手把 2 分钟间隔提成常量。

#### ⑩ 删除书目时清掉封面缩略图 —— P2 · 小

- **为什么**：见痛点 15，纯粹的垃圾积累。
- **方向**：`delete_comic` 时按 `cover_stem(comic_id)` 删除 covers 下对应 jpg；「清理缓存」统计范围加上 covers / cover-preview（或至少在界面文案里说清楚只含解压缓存）。

#### ⑪ 手动修正章节类型 —— P2 · 小

- **为什么**：见痛点 7，关键字启发式总有误判，自用最合理的解法不是把启发式做复杂，而是给一个手动兜底。
- **方向**：系列页章节列表上允许把某话的类型改成 话/卷/机翻/其他，写回 `chapters.special_kind`。改完排序立即生效。

### 3.3 体验 / UX

#### ⑫ 阅读器"跳页"与临时放大 —— P1 · 小~中

- **为什么**：见痛点 13。跳页是查资料型重读的刚需；放大是看清对话框小字 / 大跨页细节的刚需，现在只能切"原图"适配再切回来。
- **方向**：页码标签（`reader-page-count`）点击变成输入框回车跳转（小）；放大做最简版：Ctrl+滚轮缩放 + 拖拽平移 + 按 0 复位，只在翻页/双页模式下生效（中）。不做平滑动画、不做小地图。

#### ⑬ 书库网格二维键盘导航 —— P2 · 小

- **为什么**：见痛点 12，既然已经做了键盘选中（`selectedIndex` + 高亮 + `scrollIntoView`），把"下"键修对就是顺手的事。
- **方向**：根据当前每行列数（可用容器宽度 / 卡片宽度算，或读 `getBoundingClientRect` 分组）让 ArrowDown/Up 走整行步长。

#### ⑭ 滚动模式占位高度记忆 —— P2 · 小

- **为什么**：见痛点 14，长条漫画滚动条跳动影响"读到哪了"的空间感。
- **方向**：最简单的改良：用"本章已加载图片的平均高度"代替写死的 900 作为未知页的估计值，一行改动就能明显缓解；进一步可以把每话的实测高度表随进度一起缓存（中等工作量，先不必）。

#### ⑮ 扫描期间界面反馈已足够，补一个"上次扫描时间" —— P2 · 小

- **为什么**：静默自动扫描成功时不弹任何消息（`runScan` 的 quiet 分支），用户无从知道"书架有没有被检查过"。
- **方向**：侧栏底部状态行（`sidebar-footer`）在空闲时显示"上次检查：xx:xx"，数据就是现成的 `lastScanAtRef`。

### 3.4 UI / 视觉

#### ⑯ 封面网格密度选项 —— P2 · 小

- **为什么**：书越多，"一屏能扫过多少本"越影响找书效率。现在卡片尺寸固定（`App.css` 的 `.library-grid`）。
- **方向**：书库工具栏加"大 / 中 / 小"三档，切 CSS 变量（`--tile-width` 之类），存 localStorage。不做列表视图，网格三档足够。

#### ⑰ 夜间模式下的阅读底色微调 —— P2 · 小

- **为什么**：阅读区底色影响夜间长时间阅读的舒适度；目前 reader-stage 底色跟随主题，白边漫画在夜间会很刺眼。（假设：具体刺眼程度取决于个人书库里图片的裁边情况，建议先自己夜里读两话确认再动手。）
- **方向**：阅读器"更多"菜单加底色选项：纯黑 / 深灰 / 跟随主题。一个 CSS 变量的事。

#### ⑱ App.css 按功能拆文件 —— P2 · 小

- **为什么**：1448 行单文件找样式靠搜索。纯粹的整理项，不改任何视觉。
- **方向**：拆成 `base.css` / `library.css` / `reader.css` / `settings.css`，在 `App.tsx` 或各 feature 入口分别引入。建议和 ⑤ 一样"改到哪拆到哪"，不专门做。

## 四、建议排期

一个人执行，按"先保数据、再修正确性、然后攒舒适度"的顺序。每一批做完都跑 `npm run verify`、真机开自己的书架读两话，确认没退步再进下一批。

**第一批：兜底（P0，全部小改动）**
1. ① 索引库自动备份 —— 做完这条，后面所有改动的心理压力都会小很多。
2. ② 半话排序修复 + 顺手修痛点 8（User-Agent 版本号）和痛点 2（rar 页数 `unwrap_or(1)` 改成显式的"未知页数"处理）。

**第二批：日常摩擦（P1 小项，见效快、风险低）**
3. ⑨ 自动扫描开关、⑮ 上次扫描时间（两者相邻，一起做）。
4. ⑥ 缓存清理降频。
5. ⑧ 标记已读/未读。
6. ⑫ 的"跳页"部分。

**第三批：清理与收敛（趁热打铁，为后面中型改动铺路）**
7. ③ 死代码 / 旧文档清理。
8. ④ 路径逻辑收敛到 Rust。

**第四批：中型体验项（一次只做一个）**
9. ⑦ zip 边解压边看（本批最值的一项，建议先做）。
10. ⑫ 的"临时放大"部分。

**第五批：随缘项（P2，哪个痒了修哪个）**
- ⑩⑪⑬⑭⑯⑰ 按当时的实际不爽程度挑着做。
- ⑤⑱（拆 Hook、拆 CSS）不单独排期，绑定在"下次要大改那个文件时"顺手做。

原则上第一、二批不要跳过或调换——它们风险最低、收益最直接；后面的顺序都可以按心情调整。

## 五、明确不做

以下事项对个人自用工具是纯负担，明确排除（其中多数在 `docs/superpowers` 的旧设计里也早已排除过，这里重申并补充）：

- **任何联网内容功能**：在线漫画源、爬虫、订阅更新、元数据刮削（如从 AniList / Bangumi 拉简介评分）。数据只来自本地文件夹，这是本项目最大的简单性来源。
- **账号、多用户、同步、云备份**。备份就是复制到本机另一个目录（见 ①），最多自己手动把备份目录放进网盘同步文件夹。
- **多平台**：不做 macOS / Linux / 手机 / 平板适配，不做 Web 版。代码里 `cfg(windows)` 的假设可以继续放心用。
- **数据库层的过度工程**：不引 ORM、不做连接池、不做读写分离。一个用户一个 sqlite 文件，rusqlite 直连就是正确答案。
- **前端过度工程**：不引 Redux/Zustand 等状态库，不引 UI 组件库，不做列表虚拟化（几百本的规模 `loading="lazy"` 足够），不做并行扫盘。
- **流程仪式**：不加 PR CI 流水线（本地 `verify` 就是 CI）、不写 CHANGELOG、不做语义化发版自动化、不加遥测 / 崩溃上报。
- **格式军备竞赛**：不内置 rar 解压库（外部 7-Zip/WinRAR 方案维护成本几乎为零）、不支持 pdf / epub / 7z——真遇到再说，遇不到就是白写。
- **AI / 推荐类功能**：不做推荐、不做自动打标签。自己的书架自己最清楚。
